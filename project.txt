Great question. Here's the priority order I'd recommend based on dependencies:

1. Dockerfile — yes, start here
The app is already built. The Dockerfile defines how it runs in production. Currently it's just FROM node:18-alpine AS builder — no WORKDIR, COPY, RUN npm ci, EXPOSE, or CMD. Without this, nothing downstream can deploy.

2. IAM module (no dependencies)
You need roles/policies before any AWS service can act. Write the IAM module first — instance profiles for EC2, ECS task roles, CodeDeploy role, etc.

3. Security Groups module (depends on VPC)
You can't launch anything without SGs. Write this after VPC but before RDS/ALB/ASG since they all need SG references.

4. RDS module (depends on VPC + SGs)
The backend needs a database. RDS is fairly self-contained once it has a subnet group and SG.

5. ALB module (depends on VPC + SGs)
Needed before the ASG because the ASG attaches to the target group.

6. EC2-ASG module (depends on VPC + SGs + IAM + ALB)
This is the most complex — it ties everything together: launch template, user data script, ASG config, and ALB attachment.

7. S3-CDN module (independent)
Frontend hosting via S3 + CloudFront. Mostly standalone.

8. Monitoring module
CloudWatch alarms, dashboards, SNS. Can be done anytime but best after everything is deployed.

9. CI/CD (GitHub Actions)
Only makes sense once the infrastructure exists to deploy to.

1. Dockerfile first.

So, first a dockerfile is a plain text file that contains the instructions to build a docker image which is like the environment a docker container
should run on. A safe haven for the docker container.

for nodejs applications, or any applications that require unnecessary folders to be
prevented from copying, you make a .dockerignore file in the root directory.

Typically for a nodejs app, the dockerfile format goes as follows:

FROM [image, "node:22-alpine"]

WORKDIR /usr/src/something - set workdirectory first

COPY package.json package-lock.json - copy the package.json files right after

RUN npm install -production - Run the npm install command and add the production
                                tag to tell docker to only install the production
                                dependencies

EXPOSE [port] - next expose the port of the app

CMD ["npm, "run", "build"] - Finally the run command for the applications

- Since the whole app is divided into backend and frontend, we are gonna need
a third component to connect these 2 together.

Which is a docker-compose file, it is a standard tool to connect and orchestrate
multiple containers together.

It is written in yaml format, the name must be "docker-compose.yml" or ".yaml"

The reason: The backend was enforcing ssl but since this was ran in a local environment, postgres wasnt using ssl, so the backend server refused it.
It happened because of this line in db.js

ssl: process.env.PGSSL === 'true' || process.env.NODE_ENV === 'production'

The fix? Set PGSSL: inside docker compose file set gpssl false in backend service

OK the above fix didnt work, so we had to rewrite the logic in db.js to allow the above fix to work.
What we changed? 

ssl: process.env.PGSSL === 'true' ? { rejectUnauthorized: false }
          : process.env.PGSSL === 'false' ? false
          : process.env.NODE_ENV === 'production' ? { rejectUnauthorized : false } : false 

Allows the PGSSL: false parameter to actually do its job.
